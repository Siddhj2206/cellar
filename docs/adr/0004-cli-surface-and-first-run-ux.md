# CLI surface: verb-first with object groups; popup as presentation mode

Status: accepted (wayfinder #23, 2026-08)

Cellar's CLI is verb-first at the top level for artifact actions — `cellar install <path>` (the flagship, installer-aware), `cellar launch <app>` (daily driver), `uninstall`, `list`, `doctor` — with two noun groups for lifecycle objects (`prefix`, `runner`). The rule for implementers: *actions on artifacts are top-level verbs; objects with lifecycle get noun groups*. `cellar install <path>` is always an artifact; managed runtimes are `cellar runner install`, so the single verb stays unambiguous. The first-run "popup" is a presentation mode of the same InstallSession application service (interactive TTY flow now, GUI dialog later), wired from file associations straight to the presentation binary — never a separate program.

## Considered options

- **Pure noun-verb surface** (docker-style `cellar app install`): rejected — buries the flagship verb two words deep and adds a noun layer to every daily action.
- **Separate popup binary / shell wrapper in the MIME exec line**: rejected — duplicates the application service and breaks the symmetric-presentation rule (#20).
- **Magic exit-code mapping for game exits**: rejected — #7 propagates the game's code raw; Cellar errors are 0/1/2 with the collision documented.

## Consequences

- The surface is contractual once muscle memory forms: top-level commands, flag names, and exit codes (0 / 1 / 2, launch passthrough) change only through deprecation, never renames (clig.dev).
- New commands slot in under one stated rule, so implementers can't invent conflicting CLIs.
- The future GUI reuses every §8 use-case entrypoint unchanged — only the chrome differs.
- Extension (2026-08, implemented in #33): the desktop-integration subsystem gets a third noun group under the rule — `cellar desktop sync` re-derives launcher entries, icons, and the Open-with-Cellar association from the tree (the "cache re-derivable at any time" contract needs an invocation surface; subsystems with no artifact/lifecycle home follow the noun-group shape). A future desktop command lands under the same group.
- The `runner` noun group's managed surface lands with #34: `runner install <provider> <version>` — the version is an explicit pin (no silent "latest": the artifact is named deterministically by its release tag), downloads resumably, verifies, extracts, probes, and records; `runner list` shows managed plus discover-only rows (read-only). The group's future verbs (`update`, `remove`) land as extensions under the same rule. Extension (2026-08, #65) amending this bullet: an omitted version pin — or the literal `latest` — resolves through the provider's *declared* release feed (`ReleaseSource.latest_url`, the releases-latest page whose redirect names the newest tag) and installs that concrete tag. The amendment keeps the #34 stance's substance: resolution is explicit (a manifest field, never derived or guessed from URL templates), happens once inside the storage pipeline, a provider without a feed refuses `latest` loudly, and everything downstream — probe, inventory, `runner list`, re-install idempotency — sees only the concrete tag, never "latest".
- The doctor's full surface lands with #35, in the locked §8 shape: four sections — tree health, exe integrity, runner integrity, plan buildable — each pass/fail with a fix hint (the §7 dispositions: SuggestInstall, reinstall, recreate, re-register; hand-edit damage surfaces with its fix and is never silently repaired). Exit code is overall health (0 healthy / 1 problems) so scripts can health-check; the `--json` shape mirrors the report and is audited in the surface sweep (#36). Extension (2026-08, #57) amending this bullet: a fifth section, **desktop integration** — the host-facing derived state the other four never see. It reports launcher entries whose Exec target no longer exists (staleness is existence-only: a target that exists but differs from the running binary is a legitimate multi-binary setup and is never flagged) and a missing or dead Open-with-Cellar association once integration has happened at all (a host with no entries directory was never integrated and passes clean). Icons are never reported — the cache is disposable — and every fix hint points at `cellar desktop sync`, except an entry whose app file is damaged (#56: sync spares it), whose finding self-reports "kept but unrepaired" instead of pointing at a fix that would not fix. The same amendment gives `desktop sync` a receipt: when a rewrite changes Exec targets it prints `Repaired N stale launcher entries` as ordinary quietable narration.
- The surface sweep (#36) makes the contract testable end-to-end. **Standard flags** (clig.dev): `-q/--quiet` is global (before or after the subcommand, any nesting depth) and silences status/summary narration — delivered data (tables, JSON, plans, reports, the `--detach` pid/log line), prompts, and errors always print; `--json` is accepted by the data commands (`list`, `prefix list`, `runner list`, `doctor`, `launch --dry-run`); `--no-input` and `-n/--dry-run` exist exactly where they mean something (install, launch); `-h/--help` and `--version` are accepted on every command (version is propagated and prints `cellar <version>` at every depth — the `runner install` positionals keep the ids `provider`/`version_pin` so the flag and the version-pin positional never collide). The blueprint's "standard flags everywhere" is interpreted by the semantics rule: *every flag exists wherever it has meaning* — a flag that would do nothing on a command is never silently accepted-and-ignored, it is a usage error (so `--no-input` on `list` exits 2). **Help teaches**: every command's help leads with an Examples block — carried by the help template, so `-h` and `--help` both teach; a bare invocation of a required-arg command — including a bare group (`cellar prefix`) or bare `cellar` — prints that command's examples-first help and exits 2 (usage), via a walker (the CLI's `deep_command`, presentation only) because clap's own missing-argument error omits examples; unknown commands and flags get "Did you mean?" suggestions (clap's, on by default). **Exit codes audited**: 0 success, 1 operation error, 2 usage; `launch` propagates the game's code raw (the 1-collision documented, never mapped); a signal-killed game exits 1 with the signal reported. **Color contract**: ANSI only on a terminal without `NO_COLOR` — any value disables, empty included (no-color.org), and that applies to clap's own help/error rendering as well, not just the data output; piped stdout is always plain and data commands degrade to plain tables (column widths always measure plain text — colors never re-flow a table); `--json` output always ends with a newline. **`--json` shapes** for `list`, `doctor`, and `launch --dry-run` (plus `prefix list` and `runner list`) are contractual and documented with samples in `docs/cli-json.md` (the machine vocabulary — including serde's default capitalization on `RunnerFamily`/`Layer` and the externally-tagged `RunnerInstall`/`ConfiguredRunner` — is stable).
- Extension (2026-08, #61) to the exit-code vocabulary: **2 = usage/config error of the environment, not of a command**. A misconfigured `XDG_DATA_HOME` / `HOME` (relative after tilde expansion — #61) makes every command die at store construction with the offending variable named on stderr and exit code 2 (clap's own usage-error shape), before any tree can be created under `$PWD`. Command failures keep 1; game exits stay passthrough.
- Extension (2026-10, #40) to the install surface: **an omitted flag on the re-register path keeps what the AppEntry already has.** `install` is the only command whose meaning depends on prior state — re-running it on an already-registered exe updates that same entry (blueprint §8), so a flag carrying a clap-level `default_value` cannot mean "reset this field" on the update path. `--kind` loses its `default_value` and becomes `Option<AppKind>`: a new AppEntry takes `Game`, an existing one keeps its kind unless a kind is named. This generalizes the rule `--name` already followed, and states the default for any future re-register flag — the absent case is *keep*, never *reset*. No flag is removed or renamed, so no deprecation window is needed; the change is to what omission means, in the direction that stops silently rewriting a field the user did not name. `--prefix` is deliberately **not** folded in yet: on the session branches an omitted prefix also chooses where the artifact runs or extracts, so "keep the entry's binding" and "the prefix this session touched" can disagree — that needs its own decision (#40, grill question 3), not a flag default.
