# Proton and umu provider shape (managed Proton only) — Research #18

**Ticket:** [#18 — Proton and umu provider shape (managed Proton only)](https://github.com/Siddhj2206/cellar/issues/18) (part of [#14](https://github.com/Siddhj2206/cellar/issues/14))
**Goal:** Recommend how `docs/rewrite-blueprint.md` should name and shape its runner/provider examples under the constraint that **Cellar manages only Proton (e.g. GE-Proton) plus a self-contained umu**; system wine and Steam Proton are discover-only. Research conducted 2026-08-22 against primary sources (GitHub repos/APIs, Valve Proton tree, umu-launcher source, POSIX spec).

## Landscape model

The constraint splits every "runner" into one of two provider modes:

* **Managed** — Cellar owns the inventory: downloads, verifies, versions, and stores the artifact in an XDG-data runtime dir; Cellar can list, upgrade, remove, pin versions. In scope: GE-Proton (and by extension the "UMU-Proton" builds), plus the umu-launcher itself.
* **Discover-only** — Cellar reads whatever the host already has (a `wine` binary on `PATH`, or Proton builds inside Steam's own layout) and never downloads, moves, or uninstalls them.

The upstream ecosystem already encodes this same split. umu-launcher's docs explicitly say protons installed in *system* paths are never searched, only its own data dirs and Steam's `compatibilitytools.d` [umu_proton.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_proton.py); and the GE-Proton README warns that running GE-Proton outside Steam is *only* supported through umu, because Proton expects to run inside the Steam Linux Runtime container [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom). So Cellar's "managed Proton + managed umu + discover-only wine/Steam Proton" is not a Cellar invention — it mirrors how the ecosystem itself divides the world.

## GE-Proton: acquisition (GitHub Releases + SHA-512), install layout, registration

### Release artifact shape

Primary evidence — the GitHub Releases API for `GloriousEggroll/proton-ge-custom` (release [GE-Proton11-5](https://github.com/GloriousEggroll/proton-ge-custom/releases/tag/GE-Proton11-5), published 2026-08-11, via [api.github.com/repos/GloriousEggroll/proton-ge-custom/releases/latest](https://api.github.com/repos/GloriousEggroll/proton-ge-custom/releases/latest)):

* Tag/name is the version string: `GE-Proton11-5`.
* Assets are per-architecture tarballs plus a matching checksum file:
  * `GE-Proton11-5-x86_64.tar.gz` (~508 MiB) + `GE-Proton11-5-x86_64.sha512sum`
  * `GE-Proton11-5-aarch64.tar.gz` + `GE-Proton11-5-aarch64.sha512sum`
* Deterministic URL: `https://github.com/GloriousEggroll/proton-ge-custom/releases/download/<TAG>/<TAG>-x86_64.tar.gz` (or `-aarch64.tar.gz`). There are exactly 6 assets per release: 2 tarballs, 2 checksums (the other 2 being source archives).

**Checksum caveat for the blueprint:** the ticket says "sha256 verification", but the primary sources publish **SHA-512** checksum files. The GE-Proton README's official download script verifies with `curl "$checksum_url" | sha512sum -c -` where `checksum_url` is `<release_name>.sha512sum` [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom); umu-launcher's downloader computes `sha512()` over the archive and compares hexdigests parsed from the `.sha512sum` asset [umu_proton.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_proton.py). The blueprint should specify SHA-512 verification against the per-release `.sha512sum` file (an additional sha256-of-file is possible but not what upstream publishes). GE-Proton is only built for `x86_64` and `aarch64`; umu filters assets the same way (`_NON_DEFAULT_ARCH_MARKERS = {"aarch64": "-aarch64"}`, unsuffixed asset = x86_64) [umu_proton.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_proton.py).

### Install layout

* The tarball extracts to a **single top-level directory named exactly the tag** (e.g. `GE-Proton11-5/`). Evidence: umu's installer computes the directory name as the archive name minus `.tar.gz` and moves that directory into the compat-tools folder [umu_proton.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_proton.py); the GE-Proton README script does the same (`release_name=${tarball_name%.tar.gz}`) and treats `compatibilitytools.d/$release_name` as "already installed" [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom).
* Interior layout is the standard Proton redistributable layout (GE-Proton is built from Valve's Proton build system via `make redist`, which "create[s] a redistribute build (`redist/`) that can be copied to `~/.steam/root/compatibilitytools.d/`" [ValveSoftware/Proton README](https://github.com/ValveSoftware/Proton/blob/proton_11.0/README.md)). Valve documents the expected tool directory as:
  ```
  compatibilitytools.d/my_proton/
  ├── compatibilitytool.vdf
  ├── filelock.py
  ├── LICENSE
  ├── proton
  ├── proton_dist.tar   (Valve redist); GE-Proton ships an extracted files/ tree instead
  ├── toolmanifest.vdf
  ├── user_settings.sample.py
  └── version
  ```
  [ValveSoftware/Proton README](https://github.com/ValveSoftware/Proton/blob/proton_11.0/README.md). The `proton` launcher script itself confirms the runtime layout it expects: `files/` (dist dir), `files/bin/wine`, `files/lib/`, `version` file, `user_settings.py`, legacy `dist/` handling [ValveSoftware/Proton `proton` script, branch proton_11.0](https://github.com/ValveSoftware/Proton/blob/proton_11.0/proton). GE-Proton additionally ships `protonfixes/` (its per-game fix system) [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom).
* **Registration/selection in Steam** (relevant because Cellar's managed dir may also be visible to Steam): (1) create a directory in `~/.steam/steam/compatibilitytools.d/` (native Steam; the Flatpak path is `~/.var/app/com.valvesoftware.Steam/data/Steam/compatibilitytools.d/`), (2) extract the tarball there, (3) restart Steam, (4) in the game's Properties → Compatibility tab check "Force the use of a specific Steam Play compatibility tool" and pick it [proton-ge-custom README — Installation/Enabling](https://github.com/GloriousEggroll/proton-ge-custom); Valve's README uses the equivalent `~/.steam/root/compatibilitytools.d/` spelling [ValveSoftware/Proton README](https://github.com/ValveSoftware/Proton/blob/proton_11.0/README.md).
* The `proton` entry script is the *launch* contract for any wrapper: it is a Python script invoked as `<proton_dir>/proton <verb> <exe> [args]`, requires `STEAM_COMPAT_DATA_PATH` (and uses `STEAM_COMPAT_CLIENT_INSTALL_PATH`, `STEAM_COMPAT_INSTALL_PATH`, `STEAM_COMPAT_LIBRARY_PATHS`), and dispatches on verbs: `run`, `waitforexitandrun` (wait for wineserver shutdown, then run), `runinprefix`, `destroyprefix`, `getcompatpath`, `getnativepath` [ValveSoftware/Proton `proton` script](https://github.com/ValveSoftware/Proton/blob/proton_11.0/proton). This verb set is what umu exposes as `PROTON_VERB` [umu_consts.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_consts.py).

### What GE-Proton adds over Valve Proton

The README's own list: "bleeding-edge Proton Experimental" Wine, media-foundation/video playback patches, AMD FSR integration, NVIDIA CUDA/NVAPI support, raw input, the `protonfixes` per-game fix system, backported upstream and wine-staging patches, NTSync enablement [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom). It is "a custom build of Proton, not affiliated with Valve's Proton". `UMU-Proton` is the parallel build for umu: Valve Proton plus "UMU compatibility", released from `Open-Wine-Components/umu-proton` with the same asset shape (`UMU-Proton-10.0-4.tar.gz` + `UMU-Proton-10.0-4.sha512sum`, built from the `proton_10.0` branch) [umu-proton releases API](https://api.github.com/repos/Open-Wine-Components/umu-proton/releases/latest).

## umu: acquisition and invocation

### What umu is

umu-launcher ("Unified launcher for Windows games on Linux", `Open-Wine-Components/umu-launcher`, GPL-3.0, Python) is "essentially a copy of the Steam Runtime Tools and Steam Linux Runtime that Valve uses for Proton, with some modifications made so that it can be used outside of Steam" [umu-launcher README](https://github.com/Open-Wine-Components/umu-launcher). Concretely: umu is `SteamLinuxRuntime_sniper` (compiled steam-runtime-tools + the runtime container) with `_v2-entry-point` renamed to `umu`, and `umu-run` replacing Steam's `steam-launch-wrapper` [umu-launcher README](https://github.com/Open-Wine-Components/umu-launcher).

### The launch chain (primary-source quoted)

Valve's own Steam launch line for a Proton game, quoted verbatim in the umu README:

```
reaper SteamLaunch AppId=348550 -- steam-launch-wrapper -- .../SteamLinuxRuntime_sniper/_v2-entry-point --verb=waitforexitandrun -- .../compatibilitytools.d/GE-Proton8-27/proton waitforexitandrun <game.exe>
```

umu reproduces this exactly outside Steam: `umu-run` takes the place of `steam-launch-wrapper`, and inside the downloaded runtime directory a symlink `umu -> _v2-entry-point` provides the renamed entry point [umu-launcher README](https://github.com/Open-Wine-Components/umu-launcher); [umu_runtime.py `_install_umu`](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_runtime.py) (literally logs `"Linking: umu -> _v2-entry-point"` after installing the runtime). The executable chain therefore is:

```
umu-run <exe> [args]
  → <runtime>/_v2-entry-point --verb=waitforexitandrun -- <proton_dir>/proton waitforexitandrun <exe> [args]
    → Steam Linux Runtime container (pressure-vessel/bwrap)
      → Proton's wineserver + wine, then the Windows executable
```

Verified from umu source: `umu_run()` → `build_command()` returns `layer.command(env["PROTON_VERB"], ...) + [EXE] + opts` and `run_command()` execs it; `PROTON_VERB` defaults to `waitforexitandrun` [umu_run.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_run.py). The layer is `CompatLayer(protonpath, <UMU_LOCAL>/umu-shim)`: it reads the Proton dir's `toolmanifest.vdf` (manifest `commandline`, e.g. `_v2-entry-point --verb=%verb%`), resolves the required runtime from `require_tool_appid` (a Steam appid per runtime), and for a `container-runtime` layer prepends the runtime's entry point with the verb [umu_runtime.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_runtime.py).

### Environment variables (the launch-plan contract)

Documented in the man page [umu.1.scd](https://github.com/Open-Wine-Components/umu-launcher/blob/main/docs/umu.1.scd) and enforced in [umu_run.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_run.py):

* `GAMEID` — game id for protonfixes lookup; **defaults to `umu-default`**; may be numeric or `umu-<id>`; `STEAM_COMPAT_APP_ID`/`SteamAppId`/`SteamGameId` are derived from it.
* `STORE` — storefront token for protonfixes (`egs`, `gog`, `battlenet`, `amazon`, `humble`, `itchio`, `ubisoft`, default `none`) [umu.5.scd](https://github.com/Open-Wine-Components/umu-launcher/blob/main/docs/umu.5.scd).
* `WINEPREFIX` — **defaults to `$HOME/Games/umu/$GAMEID`** (or `$HOME/Games/$STORE` when only STORE is set). Prefix layout mirrors Steam compatdata: `pfx/` (self-symlink), `shadercache/`, `gstreamer-1.0/`, `tracked_files` [umu_run.py `setup_pfx`](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_run.py). `STEAM_COMPAT_DATA_PATH` is set to the prefix dir, `STEAM_COMPAT_SHADER_PATH` to `pfx/shadercache`.
* `PROTONPATH` — path to a Proton dir, a **version name** (e.g. `GE-Proton9-1`, resolved inside `$XDG_DATA_HOME/Steam/compatibilitytools.d`), or a **codename** (`GE-Proton`, `UMU-Proton`, `GE-Latest`, `UMU-Latest`, `umu-scout`, …) which triggers download of the latest build; **default `UMU-Proton`**.
* `PROTON_VERB` — must be a valid Proton verb; **default `waitforexitandrun`**.
* `UMU_LOG`, `UMU_RUNTIME_UPDATE` (default on), `UMU_NO_PROTON`, `UMU_HTTP_TIMEOUT`/`UMU_HTTP_RETRIES`, and `UMU_ZENITY`/`UMU_CONTAINER_NSENTER` (auxiliary).
* A TOML config file is supported via `umu-run --config config.toml` with the `[umu]` table: `prefix`, `proton`, `exe`, `game_id`, `store`, `launch_args` [umu.5.scd](https://github.com/Open-Wine-Components/umu-launcher/blob/main/docs/umu.5.scd).

### XDG-data layout (what "managed" means)

From umu source `umu_consts.py` [umu_consts.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_consts.py) (all `XDG_*` defaults per the freedesktop basedir spec, overridable via `UMU_FOLDERS_PATH`):

* `~/.local/share/umu/` (`UMU_LOCAL`) — runtime installs, one subdir per runtime variant (`steamrt2`, `steamrt3`, `steamrt4`, `steamrt4-arm64`) + `umu-shim`.
* `~/.local/share/umu/compatibilitytools/` (`UMU_COMPAT`) — umu-managed Proton builds for `*-Latest` codenames (e.g. `GE-Latest/`, `UMU-Latest/`).
* `~/.local/share/Steam/compatibilitytools.d/` (`STEAM_COMPAT`) — named Proton builds (e.g. `GE-Proton11-5/`) are installed **here**, i.e. into Steam's own discovery dir, so Steam can also see them.
* `~/.cache/umu/` (`UMU_CACHE`) — resumable download cache.
* Locks: `umu.lock` (runtime), `compatibilitytools.d.lock` (Proton install), `pfx.lock` (prefix), via `flock(2)`.

### How umu acquires things (the acquisition pattern Cellar should copy)

* **Proton (GE-Proton / UMU-Proton):** hit `api.github.com/repos/GloriousEggroll/proton-ge-custom/releases/latest` (or `.../umu-proton/...`); select the arch-matching `*.tar.gz` + `*.sha512sum`; **verify SHA-512**; extract into `~/.cache/umu`, then move the single top-level dir into `STEAM_COMPAT` (named builds) or `UMU_COMPAT/<codename>` (`* -Latest`); skip if `compatibilitytools.d/<name>` already exists; fall back to the newest installed build on network failure [umu_proton.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_proton.py). HTTPS scheme is enforced; downloads resume from cache; a file lock serializes installs.
* **Steam Linux Runtime:** fetch `latest-public-beta.txt` from `https://repo.steampowered.com/<variant>/images/`, download `SteamLinuxRuntime_<codename>.tar.xz` with `SHA256SUMS` verification from the same endpoint, extract into `~/.local/share/umu/<variant>`, symlink `umu -> _v2-entry-point`, validate with `pressure-vessel/bin/pv-verify --minimized-runtime` [umu_runtime.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_runtime.py). Runtimes map to Proton by `toolmanifest.vdf`: sniper (appid 1628350) for Proton 8–10 era builds, `steamrt4` (appid 4183110) for new builds; soldier (1391110) is the legacy Proton-7 runtime.
* **umu itself:** released as `umu-launcher-<ver>-zipapp.tar` (the distro-agnostic artifact, ~430 KB, 406k downloads for 1.4.4) plus distro packages (.deb/.rpm) [umu-launcher releases API](https://api.github.com/repos/Open-Wine-Components/umu-launcher/releases/latest). `make install` (or `--user-install` → `~/.local/bin/umu-run`) per [umu-launcher README](https://github.com/Open-Wine-Components/umu-launcher).

## Discovery-only seam: host wine and Steam Proton

The same provider *seam* must expose runners Cellar does not own. Two read-only sources:

1. **System wine via PATH.** A plain `wine` install is invoked as `wine <exe>` and found by the standard command lookup: POSIX `execvp` semantics — if the command contains no slash, the directories in `PATH` are searched in order ([POSIX.1-2024, execvp](https://pubs.opengroup.org/onlinepubs/9799919799/functions/execvp.html)). A discover-only wine provider therefore: iterate `PATH`, find an executable named `wine` (optionally `wine64`), probe it (`wine --version` → version string), and return a `Runner` descriptor backed by that path. No inventory, no download. Note the ecosystem boundary: system wine is *not* interchangeable with Proton — GE-Proton's README warns that Proton expects the SLR container and running it outside is unsupported [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom), so the PATH-discovered wine provider is for plain-wine launches only, and never a fallback for "managed Proton".
2. **Steam Proton (and anything in Steam's compat dirs) via Steam's layout.** Valve's own docs define the discovery contract: local compatibility tools live in `~/.steam/root/compatibilitytools.d/` (Valve's spelling) [ValveSoftware/Proton README](https://github.com/ValveSoftware/Proton/blob/proton_11.0/README.md) / `~/.steam/steam/compatibilitytools.d/` (GE-Proton's spelling, used by its install script) [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom); umu reads the same directory as `$XDG_DATA_HOME/Steam/compatibilitytools.d` [umu_consts.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_consts.py). Steam-distributed Proton itself lives in `~/.steam/steam/steamapps/common/Proton #.#` (the Proton README states `user_settings.py` "is located in the Proton installation directory in your Steam library (often `~/.steam/steam/steamapps/common/Proton #.#`)") [ValveSoftware/Proton README](https://github.com/ValveSoftware/Proton/blob/proton_11.0/README.md). Discovery = enumerate directories under those two roots, read each `toolmanifest.vdf`/`compatibilitytool.vdf` for display name, and detect the launcher `proton` script — the exact mechanism umu's `CompatLayer` uses [umu_runtime.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_runtime.py). Steam decides when an entry appears in its "Steam Play compatibility tool" dropdown (restart + selection per the READMEs above); Cellar simply mirrors the same directory scan read-only.

Crucially, umu itself documents the discovery boundary: "**Protons installed in system paths will not be searched**" [umu_proton.py](https://github.com/Open-Wine-Components/umu-launcher/blob/main/umu/umu_proton.py). That is exactly the discover-only notion: the provider reads *declared locations* (PATH for host binaries; Steam's compat layout for Proton), never fabricates inventory from system paths.

## Recommendation for Cellar blueprint

1. **One provider seam, two modes.** Define a `Runner`-resolution trait with a `Managed` (owns inventory) vs `Discovered` (read-only reference) distinction. Name **four concrete provider examples**, matching the constraint:
   * `proton-ge` (managed) — GE-Proton from GitHub Releases: `GET releases/latest` → pick `<tag>-x86_64.tar.gz` + `<tag>-x86_64.sha512sum` → verify **SHA-512** (`sha512sum -c -`; the "sha256" in the ticket should be corrected) → extract to a Cellar data dir. Follow umu's install convention: write named builds into `$XDG_DATA_HOME/Steam/compatibilitytools.d/<GE-ProtonN-M>/` so Steam can also use them, or a Cellar-owned dir for strict isolation — blueprint must pick one; umu's precedent favors the Steam-visible dir.
   * `umu` (managed) — the launcher itself, versioned into `$XDG_DATA_HOME/umu/`; resolution order per the map: **configured path → managed (Cellar's pinned/downloaded copy) → PATH** (distro-provided `umu-run`). Runtime downloads (`SteamLinuxRuntime_*` from `repo.steampowered.com`, SHA-256 verified) and the `umu -> _v2-entry-point` symlink follow umu's own `setup_umu` behavior.
   * `wine` (discover-only) — `PATH` lookup (`execvp` semantics) of `wine`/`wine64`; probe version; never modified by Cellar; plain-wine launches only.
   * `steam-proton` (discover-only) — scan `$XDG_DATA_HOME/Steam/compatibilitytools.d` + `~/.steam/steam/steamapps/common/Proton *`; read `toolmanifest.vdf`/`compatibilitytool.vdf` (+ `version` file) for name/version; Cellar never owns these entries.
2. **The umu launch-plan contract is the launch contract.** Blueprint's `LaunchPlan` should carry exactly what `umu-run` consumes: `PROTONPATH` (resolved dir or version), `WINEPREFIX`, `GAMEID`/`UMU_ID`, `STORE`, `PROTON_VERB` (default `waitforexitandrun`), and the exe+args; umu fills in the rest (`STEAM_COMPAT_*`, `SteamAppId`, shader path, runtime layer). Cellar should *delegate* to an installed `umu-run` (like Heroic/Lutris do [proton-ge-custom README](https://github.com/GloriousEggroll/proton-ge-custom)) rather than reimplement the container plumbing — reimplementing pressure-vessel is explicit out-of-scope for a "runner provider".
3. **Discovery is a mirror of umu's own resolution.** For Proton, resolution order = configured path → managed-dirs (`umu/compatibilitytools`, `Steam/compatibilitytools.d`) → …; system paths are never scanned. For the wrapper binary (umu), configured path → managed → PATH. Put this exact order in the provider seam docs, and copy umu's install hygiene: flock-based per-directory install locks, resumable cache under `$XDG_CACHE_HOME`, `latest-public-beta.txt`-style version checks for self-update.
4. **Registration/selection story:** managed GE-Proton placed in Steam's compat dir becomes selectable in Steam after restart ([READMEs above](https://github.com/GloriousEggroll/proton-ge-custom)); the blueprint should treat Steam's "Force the use of a specific Steam Play compatibility tool" as the selection UI for the Steam side, and Cellar's own `list/select` for its side — same directory, two front-ends.
5. **Do not prescribe:** a second managed runner (wine-git, caffe, etc.), DXVK-as-managed-component, or any reimplementation of the umu container chain. The seam accepts future managed providers, but under the current constraint only Proton-family (GE-Proton/UMU-Proton) + umu are managed.
